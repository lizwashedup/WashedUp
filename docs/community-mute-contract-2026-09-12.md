# Community chat mute contract — source audit, 2026-09-12

This document is a local source audit and a proposed contract, not a migration or a claim about deployed behavior. Only this document was changed for this package. No database, provider, network, notification, dependency, or account operation was performed. Earlier migration comments describing live checks are historical evidence, not checks repeated here. Several saved migrations explicitly say review-only; the deployed function definitions and migration order must be verified separately before a server change.

**Baseline note:** the client-behavior paragraphs below record the pre-repair source audit. The main-room preference and matching topic-write receipt were subsequently repaired in `chat-preferences-and-plan-invites-2026-09-12.md`. The topic/event control subsequently gained scoped readback and retry handling in `topic-chat-mute-reliability-2026-09-12.md`. The pure policy now has 22 passing tests; it remains separate from the server sender. These client repairs do not resolve the delivery-time source/claim/queue contract below.

The proposed scope is **all persistent chats in one community**. It preserves each chat's saved preference underneath one community override. Event chats retain their own preference and attendance/access rules. It does not manufacture an Intros stream from the existing mixed main stream.

## Proposed additive contract

1. Add one independent, default-false persistent-chat override per `(community_id, user_id)` membership, with an authoritative preference version. A proposed name is `persistent_chats_muted`; this is not an implemented column. Expose a separate authenticated, self-only, active-member RPC accepting an explicit desired boolean and returning the saved account/community/value/version. Keep `set_community_broadcast_mute` and topic writes backward compatible. Repeating the same desired state must be safe after an uncertain network result.
2. Change only that override atomically. Do not iterate through topic memberships, save a temporary snapshot of room flags, join rooms, touch event topics, or reset unread/read timestamps. Unmute removes the override so the current underlying room preferences become effective again. If a member changes a room preference while the parent is muted, preserve the change; show that the parent still suppresses notifications.
3. Effective persistent-main suppression is `parentOverride OR broadcasts_muted`. Effective persistent-topic suppression is `parentOverride OR NOT notifications_on`. Event-topic suppression is `NOT notifications_on`; the parent override is irrelevant. Missing membership, revoked access, or unknown source/prefs is not permission to deliver. These preference predicates can only further restrict otherwise eligible recipients; they cannot grant room access or subscription.
4. Classify notification sources explicitly: main stream/member announcement, persistent topic, event topic, follower broadcast, explicit test, or another existing channel. Keep stable source-message/reaction identity for routing and dedupe. Use a topic's authoritative `explore_event_id`, not a client title, default-room flag, or missing field. Never treat `undefined`/unresolved provenance as confirmed SQL `NULL`. Main/community announcement rows need new source metadata; their present title/actor are not unique identifiers.
5. Use the same resolved policy at fanout and at each claim/retry before transport. Muted activity must not become a delayed burst on unmute: skip its push creation under the existing fanout model, or retain an explicitly terminal suppressed delivery record if the new sender needs one. Do not clear suppression or replay a muted interval on unmute. Preserve existing message history and unread counts independently of push records.
6. Define the delivery race boundary honestly. A committed mute must suppress all eligible requests that have not passed the final server delivery authorization, including queued retries. A push already accepted by a provider cannot be recalled by this setting. Atomic preference storage alone does not serialize an external HTTP send; claim/send authorization must coordinate with preference changes before claiming a stronger guarantee.
7. New reaction notifications must target the actual message author, require continuing access, exclude self-reactions/removals/no-op changes, and use the same effective room policy. They must not bypass mute because they are directed at an author. Keep broadcast multiple-reaction storage and topic single-reaction storage intact. A bounded batching/dedupe policy and current notification-permission/opt-in handling still need sender work; do not copy the legacy unbatched reaction trigger as if it satisfies the desired low-noise behavior.

Event membership stays separate: saved `sync_event_chat_membership()` inserts on RSVP and removes on cancellation/deletion. `is_topic_member()` is caller-scoped, so a service fanout evaluating many recipients must not blindly call that helper as though it accepted arbitrary recipient identities; it needs an equivalent server-authorized eligibility check. Neither preference storage nor this check should widen history access. [Attendee rules/helper](/Users/liz/Desktop/WashedUp/Implementation/chat-context-slice/supabase/migrations/20260707120000_event_chat_model.sql:40), [membership sync](/Users/liz/Desktop/WashedUp/Implementation/chat-context-slice/supabase/migrations/20260707120000_event_chat_model.sql:104).

## Saved, failed, and unknown UI states

- Loading: show that the setting is being checked; do not render missing data or a read error as “notifications on.”
- Saving: keep the requested action pending and prevent duplicate conflicting toggles. An optimistic visual change is provisional until the returned account/community/version matches.
- Confirmed muted: “Community chats muted. Unread messages stay here.” Keep an easy **Unmute** action and a persistent indicator. Event-chat controls remain visibly independent.
- Confirmed unmuted: “Community mute is off. Each chat keeps its notification setting.” Do not claim every room is now unmuted or that device permission is enabled.
- Definite refusal/failure: retain the last confirmed value, explain that the change did not save, and offer **Try again**.
- Timeout/connection loss after submission: “We couldn’t confirm this change.” Read back the authoritative setting before deciding success/failure. Never apply an inverse toggle as compensation: the first request may have committed. Retry the explicit desired value safely, and discard completions belonging to an old account or request version.

The setting changes no provider permission and sends no push itself. A permission invitation should be contextual and dismissible; muting/unmuting must not silently trigger a system prompt or reset a previous choice. The currently saved pure notification planners are not wired into the Edge sender and are not proof of enforcement. [Pure channel planner](/Users/liz/Desktop/WashedUp/Implementation/chat-context-slice/lib/notifications/channelPlan.ts:42).

## Blockers and next useful validation

Server rollout is blocked on authoritative deployed definitions, explicit source metadata, and a reviewed claim/retry policy. Older queued `community_broadcast` rows cannot reliably be distinguished between member-stream, follower, and test notifications from their saved type/title/actor alone. Do not infer a room or mass-suppress a different channel. Resolve the legacy queue/cutover policy before promising comprehensive parent-mute delivery enforcement. The main audience-count preview must also use the effective predicate once it ships, since it currently counts only `broadcasts_muted=false`. [Audience count](/Users/liz/Desktop/WashedUp/Implementation/chat-context-slice/lib/creatorMode.ts:907).

The next worthwhile code is a **pure contract evaluator with synthetic fixtures**, not a provider change: accept an explicit source classification, recipient eligibility, and saved room/parent preferences; return eligible/suppressed/unresolved with a reason, without modifying input. Test both parent values against both room values; new optional rooms while muted; room changes under the override; event attendee without community membership; event chat in a muted community; removed membership; unknown provenance/preferences; account mismatch; stale/ambiguous mutation receipts; and muted queued notifications remaining suppressed after unmute. A separate source-routing fixture should reject ambiguous legacy `community_broadcast` rows and require the same resolution at fanout and retry. Those tests would validate the proposed semantics, not prove SQL atomicity or real push delivery.

Root's local transition-manifest/history-preservation rehearsal remains separate. This document adds no SQL, provider code, runtime preferences, group creation, notification sender, or history migration.
